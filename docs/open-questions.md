## Bionic boosters and electrobanks

What the read-only view relies on, from the decompiled `BionicUpgradesMonitor`, `Electrobank`, `RemoteWorkerCapacitor`, `RemoteWorkerDock` and `BionicMinionConfig`, checked against `mithro-06-maximum-cycle-4770.sav` (the only fixture with bionics):

- A bionic is a `BionicMinion` object with four `Storage` components, added in this order: default, battery, upgrades, oxygen tank. The storage ids (`BionicBatteryStorage`, `BionicUpgradeStorage`) are not saved. The view takes the second storage as the battery and finds boosters by their `BionicUpgradeComponent` behavior in any storage. Order is an assumption from the prefab code; nothing in the save confirms it.
- An installed booster is a stored object with a `BionicUpgradeComponent` behavior whose `assignee_slotInstanceID` is `BionicUpgrade`, `BionicUpgrade2` … `BionicUpgrade8` (slot 1 has no number).
- An electrobank is a stored object with an `Electrobank` behavior holding `charge` in joules. `Electrobank.capacity` is 120000. An `EmptyElectrobank` has no `Electrobank` behavior, so it has no charge to read.
- A remote worker's `RemoteWorkerCapacitor.charge` is in joules, capacity 60. The dock's `RemoteWorkerDock.worker` is a reference by `KPrefabID.InstanceID`.
- Unlocked slots are not saved. The view computes them as the `BionicBoosterSlots` base (2) plus the `ExtraBionicBooster*` perks of mastered skills (BionicsA1 +1, A2 +1, A3 +2, B2 +1, C2 +1; `ExtraBionicBooster5` is granted by no skill), clamped to 0..8. Bank places are the `BionicBatteryCountCapacity` base (4) plus 2 with BionicsC3. Traits or effects that change these attributes would not be seen. On `mithro-06` every installed booster sits in a computed-unlocked slot.
- The internal battery maximum is 120000 per bank place (the base 480000 plus 120000 per place above 4, from `BionicBatteryMonitor`).
- Booster display names are localized strings the extractor does not read, so the view shows the id.

Installing a booster would need, none of it done or verified in game:

1. A new object for the booster (`Booster_*` prefab, whose behaviors we would have to copy from an existing instance), with a fresh unique `KPrefabID.InstanceID`, placed in the upgrade storage's saved item list.
2. An assignment that agrees with it: `assignee_identityRef` and `assignee_slotInstanceID` on the component, plus the matching side on the duplicant's assignables (the `Ownables` slot), which we have not located in the save.
3. `BionicUpgradeComponent`'s own state machine data inside the duplicant's `StateMachineController` blob. `BionicUpgradesMonitor.UpgradeComponentSlot.installedUpgradePrefabID` is `[Serialize]`d there, in an opaque blob of about 35 KB that the parser keeps as raw bytes. Editing it means decoding and re-encoding that blob.
4. Attribute effects: boosters add attribute modifiers and wattage costs to the battery monitor, which the game recomputes when it starts the booster's state machine. Unknown whether a loaded save needs the modifiers saved too.

Charging a bank would need:

1. For a charged bank, setting `charge` (at most 120000) is a single float. Likely safe, but not verified.
2. For an empty bank, the game swaps the object for a different prefab (`Electrobank.ReplaceChargedWithEmpty`), so charging means replacing the stored object, with new `InstanceID` and behaviors, not editing it.
3. `BionicBatteryMonitor` keeps `ChargedElectrobankCount` and `DepletedElectrobankCount` as state machine parameters in the same opaque blob; they may need to agree with the storage contents. Unknown whether the game recounts on load.
4. The `BionicInternalBattery` amount is already editable and may be what the game actually draws from; how it relates to the banks is unverified.

## Duplicant amount maximums

The editor clamps a duplicant's amounts to the game's range (`Database/Amounts.cs`, `BaseMinionConfig`, `MinionConfig`; see `DUPLICANT_AMOUNT_LIMITS` in `apps/web/src/worker/model.ts`). Checked against every fixture: no saved value exceeds its derived maximum. Not confirmed in game:

- Breath is the only amount whose maximum moves: the `Minnow` trait (+400) and the Swimming skill (+100). Both come from the decompile and are read from the save's trait and skill lists. A mod or a game update that adds another `BreathMax` source would make the cap too low.
- An amount outside the table (a modded one) has no derivable maximum. It stays editable and unclamped, and the UI says so.
- Bionics have no calories amount (`MAX_CALORIES = 0`), so a `Calories` entry on a bionic is left unclamped.
- Importing a duplicant profile (`applyProfile`) can change traits and skills without re-clamping breath. The game does not clamp a loaded value (`AmountInstance.value` is a raw serialized float; clamping happens on the next `SetValue` or `ApplyDelta`), so an imported profile could leave breath above a lowered maximum until then.
- The Swimming skill needs `DLC5_ID`; the editor trusts the mastery list in the save and does not check the DLC.

Citations are to the decompile (`Kupie/ONI_Decomp`, `Assembly-CSharp/` unless noted); the "fixtures" evidence comes from scanning all 10 fixtures (every `Minion` and `BionicMinion`) for each id the duplicant owns.

### What the copy does not carry over

- **Assignments** (beds, other `Ownable`s, equipment): they live on the building as `assignee_identityRef` pointing at the proxy id. The copy's proxy is new, so nothing points at it and the copy has no bed. Fixtures: the only references to a duplicant's proxy are `Bed.Ownable.assignee_identityRef` (one per duplicant).
- **Held items**: see `Storage` above.
- **Chores**: `ChoreDriver` saves no fields in the fixtures (empty template) and chores are rebuilt by the game. The state machine blob can carry a current state mid-chore. Its `masterTarget` is rewritten; any other reference stays as it was (see risks).
- **Report history** (`ReportManager`): reports key by the duplicant's instance id and name. They are history, not live references. The copy has none.

### Checked, not dangling

- `Schedule.ClearNullReferences` (`Schedule.cs:55-58`) drops schedule entries that no longer resolve, so a stale schedule id is harmless, but the copy's id resolves anyway.
- Nothing else in any fixture holds a duplicant's own id outside `ReportManager`, the proxy, the `Bed` ownables and the schedules (full scan of every template field, stored item and raw blob).
- The world or asteroid inventory is not saved: it is rebuilt at load from the objects (`Pickupable` registration), so there is nothing to patch.

### Refused

- **Bionics (`BionicMinion`)**: their boosters (`BionicUpgradeComponent`) and battery banks are stored objects that point back at the duplicant, and the state machine parameters count the banks (`BionicBatteryMonitor`, see "Electrobank charge" above). Dropping them would leave the counts disagreeing with the storage; keeping them would give one booster two owners. Not safe to rebuild, so the edit throws and the buttons are disabled.
- A duplicant with no `MinionAssignablesProxy` that points back at it, or with no `masterTarget` in its state machine data, is refused.

### Open risks (not verified in game)

1. The state machine blob is opaque. A non-owner reference inside it (one fixture duplicant has a `SeaTree` id; others hit small coincidental ids) is copied as is, so the copy may briefly hold the same target as the original. The ids exist, so it does not dangle.
2. The copy starts on the original's saved state machine state (for example mid-sleep or mid-chore). The game should re-evaluate on load; not seen.
3. Two duplicants share a `personalityResourceId`. The game allows it for imported duplicants, but the printing pod and `StoredMinionIdentity` code were not checked for it.
4. Nothing here has been loaded in the game.
